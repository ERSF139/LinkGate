## D-001 未知消息类型怎么处理

- **背景**

  DeviceLink 的 `parseFrame` 不检查类型值。未知类型只要帧头、长度上限和 CRC 过关，就会原样交给客户端，客户端打一条日志后忽略。

  网关如果也这样做，第 6 节的「长度是否和类型匹配」对未知类型就没有依据。噪声可以放一个未知类型、长度写成 4000 的假帧头，网关仍要攒满 4008 字节才发现不对。帧头检查太晚的问题会回到网关上。

- **备选方案**

  1. 未知类型视为非法帧，立刻拒绝，然后按第 7 节重同步。
  2. 未知类型只检查长度不超过 4096，CRC 通过后原样转发给订阅者。这样旧网关遇到以后新增的类型时，不会把它当成坏帧丢掉。

- **决定**

  采用方案一。版本 `0x01` 只接受 Sample 和 Heartbeat。其他类型值在帧头阶段拒绝。

- **理由**

  版本号字段就是用来划代的。`0x01` 这一代的类型表是封闭的，新消息类型属于下一代格式，应该把版本号改掉，而不是在同一版本里混进不认识的类型。

  旧实现看到新版本号，第 6 节的第二步就能用 6 字节帧头拒绝，不必为了「也许以后会加类型」把长度检查放宽。方案二把向前兼容放进类型字段，未知类型又只剩「不超过 4096」这一条约束，假帧头可以重新逼网关等待上千字节。

- **代价**

  同一版本上不能悄悄增加消息类型。新类型要提升版本号，旧网关会拒绝新版本的帧，直到网关升级。DeviceLink 客户端今天那种「收到未知类型就记日志并忽略」的路径，在 LinkGate 上不会出现，因为这种帧到不了订阅者。

  升级要有顺序。先升级网关，过渡期间网关同时接受 `0x01` 和 `0x02`，然后再升级设备。订阅者也不能落在后面：DeviceLink 的 `parseFrame` 会拒绝版本号不是 1 的帧，网关不能把新版本的帧原样转发给还没升级的客户端。新版本的数据只交给已经认识新版本的订阅者，或者先由网关转换成旧订阅者认识的格式。

## D-002 线程模型：共享 IO 线程池，按 loop 分片

- **背景**

  网关有两类连接：上万条设备连接，和少量订阅者连接。一台设备的一帧要发给所有订阅者，而订阅者可能落在任何一个 IO 线程上。连接的状态（缓冲区、Channel）只能在它所属的 loop 线程里读写，否则每次读写都要加锁。

- **备选方案**

  1. 设备端口和订阅端口各用一个线程池。每一帧都必然跨线程。
  2. 全局一张订阅者表加一把锁，设备线程直接调用订阅者连接的 `send`。`send` 在别的线程里调用会把数据拷贝一份再投递，锁和拷贝都在热路径上。
  3. 两个端口共享同一组 IO 线程。每个 IO 线程一个 `Shard`，持有落在这个线程上的订阅者、设备空闲时间轮和计数器；设备线程把一次读事件里解析出的所有合法 Sample 拼成一个批次（`shared_ptr<const Batch>`），同线程的订阅者直接发送，其他线程每个只投递一次任务。

- **决定**

  采用方案三。

- **理由**

  - 连接状态只被一个线程访问，`TcpConnection` 自身完全不需要加锁，TSan 能验证这一点。
  - 跨线程的成本按"批次 × 线程数"计算，而不是"帧 × 订阅者数"：一次读事件可能解析出几十帧，只投递一次；数据只分配一次，靠引用计数在线程间共享。
  - 没有订阅者的 Shard 直接跳过（读一个原子计数），订阅者集中在少数线程时不产生无用的唤醒。
  - 唯一跨线程共享的可变状态是设备 ID 注册表（D-009），访问频率是"每条连接一次"，用一把普通的互斥锁足够。

- **代价**

  - 设备线程和订阅者线程不同时，转发多一次 eventfd 唤醒和一次任务调度，延迟比同线程略高。
  - 关闭顺序变得重要：线程池逐个停止时，还在运行的 IO 线程不能再往已经退出的 loop 投递任务。`Hub::stop()` 加上每个 loop 一次同步屏障来解决（见 bugs.md B-003）。
  - 每个 Shard 一份计数器，读统计时要把所有 Shard 加起来；计数器按 64 字节对齐，避免伪共享。

## D-003 慢订阅者：丢它的数据，不反压设备

- **背景**

  订阅者（DeviceLink 客户端）可能卡住：界面冻结、进程被挂起，或者机器断电。网关继续给它发，它的输出缓冲就会无限增长。DeviceLink 模拟器今天就有这个问题，只是规模小暴露不出来：`broadcastSample` 不检查 `bytesToWrite()`。

- **备选方案**

  1. 不处理，靠内存撑。一个卡住的订阅者在一万台设备的负载下每小时会吃掉 1.5 GB 左右。
  2. 反压上游：订阅者慢了，就暂停读取设备连接（停止关注 `EPOLLIN`），让 TCP 流控把压力传回设备。
  3. 只对这个订阅者降级：输出积压超过高水位就暂停给它发（这段时间的数据对它丢弃并计数），回落到低水位以下再恢复；连续暂停超过 `stall_timeout` 就断开它，由客户端自己的指数退避重连。

- **决定**

  采用方案三。默认高水位 4 MiB、低水位 1 MiB、停滞超时 10 秒。

- **理由**

  - 这是扇出场景：一台设备的数据要给所有订阅者。方案二会让一个慢订阅者拖慢所有设备、所有其他订阅者，是典型的队头阻塞。
  - 监控数据是"最新值"语义，丢掉卡住期间的采样对这个订阅者影响有限；它恢复后看到的是新数据，DeviceLink 的曲线和告警都基于新数据工作。
  - 高低水位之间留出回差，避免在阈值附近反复暂停、恢复。
  - 断电的订阅者永远不会恢复，停滞超时把它清理掉，释放内存和连接。

- **代价**

  - 被暂停的订阅者会看到数据缺口，网关只计数（`subscriber_dropped_samples`），不通知订阅者。
  - 判断依据只看"已经积压的字节"，不把将要发送的这一批算进去（否则一个比高水位还大的批次会让积压为 0 的订阅者也被判慢，见 bugs.md B-001）。因此单个订阅者的输出缓冲上限是高水位加一个批次。

## D-004 epoll 用水平触发（LT）

- **背景**

  epoll 有水平触发（LT）和边缘触发（ET）两种模式。ET 只在状态变化时通知一次，必须一直读到 `EAGAIN`，否则剩下的数据不会再有通知。

- **备选方案**

  1. LT：只要还有数据可读就一直通知。
  2. ET：通知次数更少。

- **决定**

  采用 LT，所有 fd 都是非阻塞的。

- **理由**

  - LT 下每次可读事件只读一次（`readv` 加 64 KiB 栈上临时空间），一个高速连接不会饿死同一线程上的其他连接；ET 必须读到 `EAGAIN`，要么一次读很多，要么自己实现读取配额。
  - 漏读在 LT 下只是多一次唤醒，在 ET 下是连接"卡死"，而且很难测出来。
  - 写事件只在输出缓冲非空时才关注（`EPOLLOUT`），LT 下不会出现空转。
  - 监听 socket 在 fd 耗尽时会在 LT 下持续可读，用预留 fd 的办法处理（Acceptor 的 `reserve_fd_`）。

- **代价**

  高负载下系统调用次数比 ET 多。压测（docs/perf.md）里如果 `epoll_wait` 成为热点，再考虑对设备连接改用 ET。

## D-005 空闲连接检测用引用计数时间轮

- **背景**

  设备连接如果在超时时间内没有发来任何合法帧，就要断开。这包括一种攻击：发一个合法的帧头，然后一个字节一个字节地慢慢发，永远凑不成整帧。连接数是上万级，每条连接收到合法帧时都要"续期"。

- **备选方案**

  1. 每条连接一个定时器（`run_after`），续期时取消再新建。定时器队列是有序集合，续期是 O(log n)，而且上万个定时器频繁增删。
  2. 最小堆，所有连接的到期时间放在一起。续期需要能在堆里定位并调整元素，实现复杂。
  3. 时间轮：每个 IO 线程一个，若干个槽，每个槽是一组条目的强引用。收到合法帧时把条目放进最新的槽（O(1)，同一个槽里自动去重）；每个 tick 清空最老的槽。条目的析构函数就是超时动作：它的最后一个强引用随槽释放，说明这段时间里没有续期。

- **决定**

  采用方案三。槽数 = ⌈空闲超时 / tick⌉ + 1。

- **理由**

  - 续期和到期都是 O(1)，与连接数无关。
  - 不需要"取消"操作：连接正常断开后，条目里只有它的 `weak_ptr`，析构时发现连接已经不在就什么都不做。
  - 只认合法帧续期，所以慢速发送假帧头的连接会被踢掉（`TricklingFakeHeaderDoesNotKeepDeviceAlive` 测试）。

- **代价**

  - 精度是一个 tick：实际超时落在 (超时, 超时 + tick] 之间。
  - 已断开连接的条目要等它所在的槽转到才释放，最多占用一个超时周期的内存。

## D-006 启动失败抛异常，运行期错误返回错误码

- **背景**

  网络代码里有两类错误：启动时拿不到 socket、端口被占用；运行时单条连接被对端重置、写入时对端已关闭。

- **备选方案**

  1. 全部用返回码。
  2. 全部用异常。
  3. 启动期的失败抛 `std::system_error`；运行期的单连接错误返回 -1 并保留 errno，由连接自己处理（关闭这条连接），不影响其他连接。

- **决定**

  采用方案三。

- **理由**

  - 启动失败时程序本来就无法继续，异常能直接带着 errno 和上下文冒到 `main`，打印一条清楚的错误后退出码为 1。
  - 运行期的连接错误是常态（对端随时可能断开），不是"异常"；如果用异常，事件循环里任何一个回调抛出都会终止整个进程。
  - 例外：`Connector` 在 fd 耗尽时 `socket()` 会抛异常，它在事件循环内部，所以捕获后按普通失败处理并退避重试。

- **代价**

  两套风格并存，读代码时要分清某个函数属于哪一类（`socket_ops.h` 的注释写明了这一点）。

## D-007 只支持 IPv4

- **背景**

  DeviceLink 的模拟器和客户端都在局域网或本机上通信，默认地址都是 IPv4。

- **备选方案**

  1. 只支持 IPv4（`sockaddr_in`）。
  2. 同时支持 IPv4 和 IPv6（`sockaddr_storage`，`getaddrinfo`）。

- **决定**

  只支持 IPv4。

- **理由**

  当前部署环境用不到 IPv6；把地址类型封装在 `InetAddress` 里，以后加 IPv6 只影响这一个类和 `socket_ops`。

- **代价**

  IPv6-only 的网络环境无法使用。

## D-008 用 signalfd 处理退出信号

- **背景**

  收到 SIGINT / SIGTERM 时要优雅退出：停止接受新连接，关闭现有连接，等 IO 线程退出。传统的信号处理函数里只能调用异步信号安全的函数，不能加锁，也不能调用 `EventLoop::quit()` 这类可能加锁的函数。

- **备选方案**

  1. 信号处理函数里只设置一个 `volatile sig_atomic_t` 标志，事件循环定期检查。退出延迟取决于检查周期。
  2. 自管道（self-pipe）：处理函数往管道写一个字节，事件循环监听管道读端。
  3. `signalfd`：在所有线程里屏蔽这些信号，把它们变成一个 fd 上的可读事件。

- **决定**

  采用 `signalfd`，由 `SignalWatcher` 封装。

- **理由**

  - 信号就是事件循环里的一个普通事件，回调在 loop 线程里执行，可以做任何事情。
  - 必须在启动任何线程之前屏蔽信号：之后创建的线程继承屏蔽字。否则信号可能被投递给某个 IO 线程，绕过 signalfd，进程被默认动作直接终止。`main` 里先构造 `SignalWatcher`，再启动网关。

- **代价**

  只适用于 Linux。屏蔽字会被子进程继承，如果以后要 `exec` 别的程序，需要先恢复。

## D-009 一台设备一条连接，按首个 Sample 绑定设备 ID

- **背景**

  DeviceLink 的模拟器在直连模式下把 5 台设备放在一条连接上。真实部署中每台设备是独立的网络端点。网关需要知道每条连接属于哪台设备，才能处理"设备重连"这类情况。

- **备选方案**

  1. 一条连接可以承载任意多台设备，网关不关心设备 ID。
  2. 增加一种"注册"消息，连接建立后先报告设备 ID。需要修改协议（提升版本，D-001）。
  3. 一台设备一条连接，连接上的第一个 Sample 里的设备 ID 就是这条连接的身份；之后出现不同的设备 ID 视为协议违规，断开连接。同一个 ID 有新连接上线时，顶掉旧连接。

- **决定**

  采用方案三。DeviceLink 模拟器的网关模式（`integration/devicelink/0002-*.patch`）为每台设备单独建立一条连接。

- **理由**

  - 不需要修改线上格式。
  - 设备重启后，旧连接往往还处于半开状态（对端已经消失，本端还没发现）。新连接顶掉旧连接，可以立刻释放旧连接，不必等空闲超时。
  - 一条连接只对应一台设备，空闲超时、计数和日志的含义都很清楚。

- **代价**

  - 一台设备只发心跳、从不发 Sample 时，这条连接不会被绑定 ID。
  - 两台设备被错误地配置成同一个 ID 时会互相顶掉，表现为反复重连；`device_id_conflicts` 计数会持续增长，可以据此发现配置错误。
