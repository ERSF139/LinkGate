# DeviceLink 线上协议规格（devproto 实现依据）

本文是 devproto 的线上格式规格。合法帧必须和 DeviceLink 已经在传输的字节一致。解析器、编码器和测试都以本文为准，不从 DeviceLink 的实现细节倒推。

## 1. 概览

一帧由 6 字节帧头、L 字节载荷和 2 字节 CRC 组成，总长 8 + L。多字节整数和浮点数都按大端存放，整数用补码。当前版本只定义两种消息：Sample 和 Heartbeat。

接收方按第 6 节的顺序检查。任何一项失败都按第 7 节重同步，一次只丢掉 1 字节。

## 2. 帧格式

| 偏移 | 长度 | 字段 | 编码 | 取值 |
| --- | --- | --- | --- | --- |
| 0 | 2 | 同步字 | 字节 | `A5 5A` |
| 2 | 1 | 版本 | u8 | `0x01` |
| 3 | 1 | 类型 | u8 | 见第 4 节 |
| 4 | 2 | 载荷长度 L | u16，大端 | 0 ~ 4096 |
| 6 | L | 载荷 | 见各类型 | 见第 4、5 节 |
| 6+L | 2 | CRC | u16，大端 | 见第 3 节 |

长度字段的上限是 4096。某种类型自己的长度比这个更严，以第 4 节为准。

## 3. CRC

算法是 CRC-16/MODBUS，参数固定为：

| 参数 | 值 |
| --- | --- |
| 宽度 | 16 |
| 多项式 | `0x8005`（按位反转后参与运算的是 `0xA001`） |
| 初值 | `0xFFFF` |
| 输入反转 | 是 |
| 输出反转 | 是 |
| 结果异或 | `0x0000` |

对 ASCII 字符串 `123456789` 的校验值是 `0x4B37`。

覆盖范围是偏移 0 到 `5+L` 的全部字节，也就是帧头加载荷，不含末尾那 2 字节 CRC。

发送时高字节在前。Modbus RTU 习惯把 CRC 的低字节放在前面，本协议把高字节放在前面。

## 4. 消息类型

版本 `0x01` 只承认下表里的类型。

| 类型值 | 名称 | 载荷长度 | 方向 |
| --- | --- | --- | --- |
| `0x01` | Sample | 必须恰好是 36 | 设备 → 网关 → 订阅者 |
| `0x02` | Heartbeat | 必须恰好是 0 | 设备 → 网关，以及网关 → 订阅者 |

订阅者不发送任何帧。心跳到不了「订阅者 → 网关」这个方向，网关不能靠心跳判断订阅者是否还活着。订阅者所在的机器突然断电时，网关只会看到发给它的数据越积越多。网关的高水位背压处理这种情况（D-003）。

长度字段即使落在 0 ~ 4096 里，只要和这张表不一致，这一帧仍然非法。

## 5. Sample 载荷

Sample 的 36 字节载荷如下。整数是补码，三个测量值是 IEEE-754 的 64 位浮点数，全部大端。

| 偏移 | 长度 | 字段 | 编码 |
| --- | --- | --- | --- |
| 0 | 4 | 设备 ID | i32 |
| 4 | 8 | 毫秒时间戳 | i64 |
| 12 | 8 | 温度 | f64 |
| 20 | 8 | 压力 | f64 |
| 28 | 8 | 振动 | f64 |

时间戳是从 Unix 纪元（1970-01-01 00:00:00 UTC）起算的毫秒数，时区按 UTC 理解。

帧这一层不检查载荷里的数值。任意 IEEE-754 位模式都合法，包括 NaN、正无穷、负无穷和 -0.0。任意 i32 设备 ID 都合法，包括负数。这些值有没有业务意义，由上层判断。DeviceLink 的 `decodeSample` 同样照单全收，devproto 拒绝其中任何一个，就会和合法帧的解析结果不一致。

测试比较浮点字段时要逐位比较。NaN 和 NaN 用数值相等判断不会成立。

## 6. 接收方校验顺序

帧头不足 6 字节时不做任何判断，原样保留，等待更多数据。缓冲区里只有 `A5 5A 99` 这 3 个字节时，版本号虽然已经出现而且不是 `0x01`，也先不拒绝。凑满 6 字节后再按下面的顺序判断。

1. 同步字是不是 `A5 5A`。
2. 版本号是不是 `0x01`。
3. 类型是不是第 4 节里的已知类型。
4. 长度是不是和第 4 节中该类型要求的长度一致，并且不超过 4096。
5. 前四项都通过之后，才按 `8 + L` 等待整帧到齐。
6. 整帧到齐后，最后核对 CRC。

前四项只需要 6 字节帧头。在 TCP 上提前用 3 个字节下结论，省下来的等待可以忽略，规则也更难写成确定的测试。统一等满 6 字节。

这个顺序的直接后果：解析器等待中的字节永远少于最长合法帧（44 字节）。DeviceLink 原来的实现最多会为一个假帧头攒 4104 字节。这一条由模糊测试和性质测试作为不变式检查（`tests/support/parser_check.cpp`）。

## 7. 重同步规则

同步字、版本、类型、长度、CRC 任何一项失败，都只丢弃当前起点的 1 个字节，然后从下一个字节重新寻找 `A5 5A`。

缓冲区末尾如果只剩一个 `A5`，先留着。它可能是下一帧同步字的第一个字节。帧头还不满 6 字节时也整段留着，这不算失败，不丢字节。

### 统计口径

丢弃字节和坏帧分开计。

重同步过程中跳过的每个字节都计入丢弃字节数。找到候选帧头之前滑过的噪声也算丢弃字节。

每拒绝一个以 `A5 5A` 开头的候选帧头，坏帧计数加 1。版本不对、类型未知、长度和类型不符、长度超过 4096、CRC 不对，都算拒绝了一次候选帧头，因此坏帧加 1，同时按上面的规则把丢掉的那 1 个字节计入丢弃字节数。

还没形成候选帧头的噪声只计丢弃字节，坏帧不加。帧头不足 6 字节而继续等待时，两个计数都不变。

守恒关系：丢弃字节数 + 已返回帧的总字节数 + 仍在等待的字节数 = 输入总字节数。

## 8. 与 DeviceLink 当前 FrameParser 的行为差异

合法帧的解析结果必须和 DeviceLink 完全一致，字段值和 CRC 覆盖范围都不能差。Sample 载荷里的 NaN、无穷、负零和负数设备 ID 也算合法帧，两边都要原样解出来。

非法帧两边最终都会丢掉，但 devproto 判断得更早。有两种情况允许两边行为不同，差分测试时都要放行。

第一种：类型是 Sample（`0x01`），长度字段却是 4000。4000 没有超过 4096，DeviceLink 会一直等到 4008 字节，算出 CRC 不对才丢弃。devproto 读完 6 字节帧头就发现 Sample 的长度必须是 36，立刻拒绝并重同步。

第二种：类型未知，但 CRC 正确。DeviceLink 会把它交给客户端，客户端打一条日志后忽略。devproto 按 D-001 在读完帧头时就拒绝它，这帧到不了订阅者。

差分测试只比较两边解析出的帧序列，不比较丢弃字节数和坏帧计数。

`integration/devicelink/0001-*.patch` 把同样的尽早拒绝规则补进了 DeviceLink 的 `FrameParser`；打上补丁后，上面两种差异都会消失。

## 9. 黄金样例

样例存放在 `tests/data/golden/frames.txt`，每行一个样例：`<名字> <整帧的大写十六进制>`。

它们由 DeviceLink 的 `tools/golden_dump` 调用 `Protocol::buildFrame` 生成：

```bash
cd <DeviceLink 目录>
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
./build/bin/golden_dump > <LinkGate 目录>/tests/data/golden/frames.txt
```

4 个样例都已和一个独立的 Python 实现逐字节核对过，全部一致。它们覆盖了 `0x00`、`0x7F`、`0x80`、`0xFF` 四类边界字节，以及 NaN、+Inf、-0.0、最小次正规数、INT32/INT64 最大值、负数设备 ID。`tests/devproto/frame_test.cpp` 和 `sample_test.cpp` 要求 devproto 的编码和解码与它们逐字节一致。
